# Modern Java (8 → 21) — Senior Production Reference

Java 8 through 21 is not a feature checklist — it is a **release train** that changed how production JVM services are written, deployed, and debugged. Lambdas and streams (see [`java-streams.md`](java-streams.md)) made collection processing declarative. Records and sealed types made domain modeling safer. Virtual threads (overview here; deep dive in [`java-concurrency.md`](java-concurrency.md)) changed the economics of blocking I/O. This note is the **migration and decision map** for senior engineers: what each LTS actually buys you, what breaks on upgrade, and where to look when production misbehaves.

## 1. Release Train Mental Model

### The six-month cadence

Since Java 9, Oracle and the OpenJDK community ship a **feature release every six months** (March and September). Not every release is an LTS (Long-Term Support) release. The cadence matters for production planning:

```
Java 8  (2014) ── LTS ── extended commercial support, massive enterprise base
Java 9  (2017) ── non-LTS, JPMS, no longer relevant as a target
Java 10 (2018) ── non-LTS, var
Java 11 (2018) ── LTS ── first "modern" baseline after 8
Java 12–16 ── non-LTS, previews incubating records, pattern matching, text blocks
Java 17 (2021) ── LTS ── records/sealed final, strong encapsulation
Java 18–20 ── non-LTS, previews for virtual threads, structured concurrency
Java 21 (2023) ── LTS ── virtual threads finalized, pattern matching complete
Java 22+ ── feature releases; pick up previews or wait for next LTS (27)
```

**Production rule of thumb:** target **LTS releases** (8, 11, 17, 21, next 27). Non-LTS releases are for early adopters and library authors who need preview features. Most enterprises skip 12–16 entirely and jump 11 → 17 → 21.

### LTS vs non-LTS support

| Release type | Who supports it | Typical enterprise use |
|---|---|---|
| LTS | Oracle (paid), Adoptium, Amazon Corretto, Azul Zulu, Red Hat — multi-year patches | Production deployments |
| Non-LTS | ~6 months of updates from Oracle; vendors may or may not backport | CI matrix, library compatibility testing |

**Interview answer:** "We standardize on LTS because security patches and vendor SLAs align with our compliance window. We evaluate non-LTS in staging when a specific preview (e.g., virtual threads in 19–20) justifies early adoption risk."

### Preview, incubator, and final features

Java uses a **preview feature** pipeline (JEP 12):

1. **Preview** — syntax/API may change; enable with `--enable-preview`
2. **Second preview** — refined based on feedback
3. **Final** — stable in an LTS or feature release

**Incubator modules** (`jdk.incubator.*`) are separate — APIs can change without preview flag semantics. Example: early HttpClient was incubator before Java 11.

**Production consequence:** never ship preview features to production unless your org explicitly accepts breakage risk on upgrade. Libraries compiled with previews cannot be consumed without the same flags.

### The "effective Java version" of your codebase

Your **source** `release` flag, **bytecode** target, and **runtime** JDK are three different knobs:

```xml
<!-- Maven compiler plugin -->
<maven.compiler.release>21</maven.compiler.release>
```

```gradle
java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}
```

- **`--release 21`** — compiles against Java 21 API surface, emits bytecode compatible with 21, blocks use of newer APIs accidentally.
- **Running on JDK 21** with bytecode compiled for 11 — works (forward compatible).
- **Running on JDK 11** with bytecode compiled for 21 — fails (`UnsupportedClassVersionError`).

### Feature accumulation model

Non-LTS releases **accumulate** into the next LTS. You do not "pick Java 15 features" in isolation — you get everything from 12–16 when you adopt 17:

| Want this feature | First available | Stable in LTS |
|---|---|---|
| `var` | 10 | 11 |
| `HttpClient` | 11 | 11 |
| Text blocks | 15 (preview) | 17 (via 15 final) |
| Records | 16 | 17 |
| Sealed classes | 15 (preview) | 17 |
| Pattern matching `instanceof` | 16 | 17 |
| Virtual threads | 19 (preview) | 21 |
| Sequenced collections | 21 | 21 |

### Production scenario: "we're on Java 11 but Spring Boot 3 requires 17"

**Problem.** Platform team standardized on 11 LTS in 2020. Product teams want Spring Boot 3.x (baseline Java 17). Builds fail with `class file version 61.0`.

**Cause.** Spring Boot 3 dropped Java 8/11 support entirely. The ecosystem moved the floor to 17.

**Solution.** Treat 17 as the new minimum for greenfield and major upgrades. Run a parallel migration track: security-patch 11 for legacy services on a sunset timeline; all new services on 21. Use `--release` and CI matrix during transition.

### Vendor distributions

Production JVMs are rarely stock `openjdk` tarballs. Common choices:

| Distribution | Notes |
|---|---|
| Eclipse Temurin (Adoptium) | Widely used, free LTS builds |
| Amazon Corretto | AWS-aligned, free LTS |
| Azul Zulu | Commercial support available |
| GraalVM / Native Image | AOT compilation; different GC/runtime tradeoffs |
| Oracle JDK | Free for many uses since 11; paid support tiers exist |

**Senior takeaway:** pick a vendor, pin a **patch** version (e.g., `21.0.4`), and automate CVE scanning — do not float `21-latest` in production.

## 2. Java 8 Lambdas and invokedynamic

### What problem lambdas solved

Before Java 8, passing behavior required anonymous inner classes — verbose, and each one generated a `.class` file. Lambdas provide **concise syntax** for functional interfaces (single abstract method interfaces).

```java
// Before
list.sort(new Comparator<String>() {
    @Override
    public int compare(String a, String b) {
        return a.length() - b.length();
    }
});

// After
list.sort((a, b) -> a.length() - b.length());
// Or
list.sort(Comparator.comparingInt(String::length));
```

### invokedynamic — how lambdas actually work

Lambdas are **not** inner classes. The compiler emits `invokedynamic` bootstrap calls to `LambdaMetafactory.metafactory`, which at runtime generates a synthetic class implementing the target functional interface.

```
Compiler sees:  (a, b) -> a.length() - b.length()
Emits:          invokedynamic bootstrap → LambdaMetafactory
Runtime:        generates synthetic class implementing Comparator
```

**Why this matters in production:**

1. **No per-lambda `.class` file** — smaller JARs, faster class loading than anonymous classes.
2. **Capturing vs non-capturing** — lambdas that reference local variables must capture them (effectively final). Non-capturing lambdas can be singletons.
3. **Serialization** — lambdas are not reliably serializable; do not put them on Kafka messages or session state.

### Functional interfaces

`@FunctionalInterface` marks interfaces with exactly one abstract method (SAM). The JDK provides dozens in `java.util.function`:

| Interface | Method | Use |
|---|---|---|
| `Function<T,R>` | `apply(T) → R` | transform |
| `Predicate<T>` | `test(T) → boolean` | filter |
| `Consumer<T>` | `accept(T) → void` | side effect |
| `Supplier<T>` | `get() → T` | lazy produce |
| `BiFunction<T,U,R>` | `apply(T,U) → R` | combine two inputs |
| `UnaryOperator<T>` | `T → T` | same-type transform |

**Composition:**

```java
Predicate<Payment> validAmount = p -> p.amount().signum() > 0;
Predicate<Payment> knownCurrency = p -> SUPPORTED.contains(p.currency());
Predicate<Payment> isValid = validAmount.and(knownCurrency).negate();
```

### Method references

Four forms:

```java
System.out::println              // instance method on arbitrary object
String::valueOf                  // static method
String::length                   // instance method on class (first arg is receiver)
ArrayList::new                   // constructor
```

### Default and static methods in interfaces

Java 8 added `default` and `static` methods to interfaces so the JDK could evolve APIs (e.g., `Collection.stream()`) without breaking every implementer.

**Production trap:** diamond inheritance conflicts when two interfaces define the same `default` method — must override explicitly.

```java
interface A { default void log() { System.out.println("A"); } }
interface B { default void log() { System.out.println("B"); } }
class C implements A, B {
    @Override public void log() { A.super.log(); } // resolve ambiguity
}
```

### Lambda and generics

Lambdas rely on **target typing** — the compiler infers types from context. When inference fails, add explicit types or cast. For deep generics interaction, see [`java-generics.md`](java-generics.md).

```java
// Target type: Comparator<Order>
orders.sort((Order o1, Order o2) -> o1.date().compareTo(o2.date()));
```

### Streams — pointer only

The Stream API is the other half of Java 8's functional revolution. Everything about lazy pipelines, collectors, `parallelStream()`, and `Optional` chaining lives in [`java-streams.md`](java-streams.md). **Do not** treat this section as a stream guide.

**One production rule from that note:** intermediate operations are lazy — a pipeline without a terminal operation does nothing.

### CompletableFuture — pointer only

`CompletableFuture` (Java 8) enables composable async programming. Executor choice, `thenCombine`, error handling, and interaction with virtual threads are covered in [`java-concurrency.md`](java-concurrency.md).

### Production scenario: lambda hot path allocation

**Problem.** Profiling shows millions of `$$Lambda$` allocations per second in a tight loop.

**Cause.** Capturing lambda `(x) -> process(x, config)` closes over `config`, creating a new object each time. Or `stream().map(x -> transform(x, heavyObject))` captures `heavyObject`.

**Fix.** Use method reference if possible (`this::transformWithConfig`), make captured values static/final singletons, or hoist the lambda to a field:

```java
private final IntUnaryOperator doubler = x -> x * 2; // one instance
```

### Production scenario: Serializable functional interface in distributed cache

**Problem.** `InvalidClassException` when caching a `Predicate` in Hazelcast.

**Cause.** Lambdas are not guaranteed serializable unless the functional interface extends `Serializable` and the lambda is non-capturing or captures serializable finals.

**Fix.** Use a named class or record implementing the interface; never serialize lambdas across JVM boundaries.

## 3. Local Variable Type Inference (`var`)

### What `var` is (Java 10+)

`var` is **local-variable type inference** — the compiler infers the type from the initializer. It is **not** dynamic typing.

```java
var list = new ArrayList<String>();  // inferred: ArrayList<String>
var name = "Sanjay";                 // inferred: String
var count = 42;                      // inferred: int
```

The variable is still **statically typed**. Once inferred, you cannot assign incompatible types.

### Where `var` is allowed

- Local variables with initializers
- Enhanced `for` loop variables
- `try`-with-resources variables
- Lambda parameters (Java 11): `(var x) -> x.length()` — mainly for annotations

### Where `var` is **not** allowed

- Method parameters, fields, method return types
- Variables without initializer
- `null` initializer (`var x = null` — cannot infer)
- Array initializers without `new` in some cases

### Production style guide

| Good | Bad |
|---|---|
| `var orders = new ArrayList<Order>();` | `var result = service.process();` (type opaque) |
| `var path = Path.of("/etc/app/config.json");` | `var map = getMap();` (raw or unknown generic) |
| `var conn = dataSource.getConnection();` | `var x = (String) obj;` (cast defeats purpose) |

**Team convention:** use `var` when the RHS type is explicit (`new`, `List.of`, factory methods). Avoid when the type carries semantic meaning not visible on the RHS (e.g., `BigDecimal` vs `double`).

### `var` and generics

```java
var map = Map.of("a", 1);           // Map<String, Integer>
var entries = map.entrySet();       // Set<Map.Entry<String, Integer>>
```

Inference follows generic types on the RHS. It does **not** widen to interfaces automatically:

```java
var list = List.of(1, 2, 3);        // inferred: List<Integer> (immutable)
List<Integer> mutable = new ArrayList<>(list); // explicit when you need mutability
```

See [`java-generics.md`](java-generics.md) for wildcard and inference edge cases.

### `var` in try-with-resources

```java
try (var in = Files.newInputStream(path);
     var out = Files.newOutputStream(dest)) {
    in.transferTo(out);
}
```

Cleaner than repeating types; still fully typed for the compiler.

### Production scenario: `var` hides a performance bug

**Problem.** Code review passes, but production shows unexpected boxing in a hot loop.

```java
var total = 0;  // inferred int — OK
for (var item : items) {
    total += item.getAmount(); // if getAmount returns Integer, unboxing every iteration
}
```

**Fix.** Explicit type documents intent: `int total` or `long total` for money in cents.

### Production scenario: `var` breaks method overload resolution readability

**Problem.** `var x = foo();` — three overloaded `foo()` methods exist; reader cannot tell which ran without IDE.

**Fix.** Explicit type at the call site when overloads differ semantically.

## 4. Records

### What records are (Java 16 final, ubiquitous from 17)

A **record** is a **shallowly immutable** data carrier. The compiler generates constructor, accessors, `equals`, `hashCode`, and `toString`.

```java
public record OrderSummary(String orderId, BigDecimal total, Instant createdAt) {}
```

Accessors use the component name — `orderId()`, not `getOrderId()` (unless you add one).

### What you get for free

```java
// Compiler generates equivalent of:
public final class OrderSummary {
    private final String orderId;
    private final BigDecimal total;
    private final Instant createdAt;

    public OrderSummary(String orderId, BigDecimal total, Instant createdAt) { ... }
    public String orderId() { return orderId; }
    // equals, hashCode, toString
}
```

### Compact constructor (validation)

```java
public record Email(String value) {
    public Email {
        Objects.requireNonNull(value);
        if (!value.contains("@")) throw new IllegalArgumentException(value);
    }
}
```

The compact constructor assigns fields automatically after validation — no redundant `this.value = value`.

### Custom methods and implementing interfaces

Records can implement interfaces, define static factories, and add instance methods:

```java
public record Money(BigDecimal amount, Currency currency) implements Comparable<Money> {
    public Money {
        amount = amount.setScale(currency.getDefaultFractionDigits(), RoundingMode.HALF_UP);
    }
    @Override public int compareTo(Money o) {
        return amount.compareTo(o.amount);
    }
    public Money plus(Money other) { ... }
}
```

### What records are **not**

| Misuse | Why wrong |
|---|---|
| JPA `@Entity` | Records are final, no setters, no lazy proxies — use classes or Kotlin data classes |
| Mutable DTO with builders | Records are immutable — use a class if you need mutation during build |
| Replacement for all POJOs | Domain entities with behavior and lifecycle are still classes |
| Deep immutability guarantee | Components are shallowly immutable — a `List<T>` field can still be mutated unless you defensively copy |

### Records vs Lombok

| | Record | Lombok `@Value` |
|---|---|---|
| Language feature | Yes | Annotation processor |
| Serialization frameworks | Improving; check Jackson version | Mature |
| JPA | Poor fit | `@Data` common (with caveats) |
| Boilerplate | Zero | Near-zero |

**Production guidance:** records for API DTOs, Kafka events, config snapshots, and internal value types. Lombok/classes for JPA entities until your stack explicitly supports records.

### Records and JSON (Jackson)

Jackson 2.12+ supports records. Enable parameter-names module for compact constructors:

```java
public record User(String id, String name) {}

// JSON: {"id":"1","name":"Ada"}
ObjectMapper mapper = new ObjectMapper().registerModule(new ParameterNamesModule());
User u = mapper.readValue(json, User.class);
```

### Production scenario: record in Kafka event schema

**Before (Lombok + manual equals bugs):**

```java
@Data @Builder
public class OrderCreatedEvent {
    private String orderId;
    private BigDecimal amount;
}
```

**After:**

```java
public record OrderCreatedEvent(String orderId, String customerId, BigDecimal amount, Instant at) {}
```

Immutable, correct `equals`/`hashCode` for dedup, safe across consumer threads without defensive copy. Schema evolution still requires compatibility rules (add optional fields via new record version or use Avro/Protobuf for evolution).

### Production scenario: record with mutable list component

**Problem.** `record Basket(List<Item> items)` — caller mutates list after construction; record appears to change.

**Fix.** Defensive copy in compact constructor:

```java
public record Basket(List<Item> items) {
    public Basket {
        items = List.copyOf(items);
    }
}
```

### Nested records and decomposition

Records compose cleanly with pattern matching (Section 6) and sealed hierarchies (Section 5).

```java
public record Address(String line1, String city, String country) {}
public record Customer(String id, Address address) {}
```

## 5. Sealed Types

### The problem sealed types solve

Open inheritance (`public class Foo extends Bar`) means **anyone** can add subclasses. The compiler cannot prove exhaustiveness in `switch` or `instanceof` chains. Sealed types **close the hierarchy** — only permitted subclasses exist.

```java
public sealed interface PaymentMethod permits CreditCard, Upi, NetBanking {}

public final class CreditCard implements PaymentMethod {
    private final String last4;
    // ...
}
public final class Upi implements PaymentMethod {
    private final String vpa;
}
public final class NetBanking implements PaymentMethod {}
```

### Permitted subclasses rules

Each permitted class must:
- Be `final`, or
- Be `sealed` itself (continuing the hierarchy), or
- Be `non-sealed` (open again for further extension)

All in the **same module** (or same package if unnamed module) unless using qualified exports.

### Sealed classes vs enums

| Use enum when | Use sealed when |
|---|---|
| Fixed set, no per-case data | Each case carries different fields |
| Singleton instances | Need records/classes per case |
| Simple ordinal behavior | Rich behavior per subtype |

```java
// Enum — fine for status
public enum OrderStatus { PENDING, SHIPPED, DELIVERED }

// Sealed — better for payment methods with different payloads
public sealed interface PaymentResult permits Approved, Declined, Pending {}
public record Approved(String authCode, BigDecimal amount) implements PaymentResult {}
public record Declined(String reason) implements PaymentResult {}
public record Pending(String reference) implements PaymentResult {}
```

### Sealed + records + pattern matching = algebraic data types

This trio replaces many Visitor/Strategy combinations. See [`java-design-patterns.md`](java-design-patterns.md) for when patterns still earn their keep.

```java
public sealed interface Shape permits Circle, Rectangle {}
public record Circle(double radius) implements Shape {}
public record Rectangle(double w, double h) implements Shape {}

static double area(Shape s) {
    return switch (s) {
        case Circle c -> Math.PI * c.radius() * c.radius();
        case Rectangle r -> r.w() * r.h();
    }; // exhaustive — no default needed
}
```

### Production scenario: new payment type missed in reconciliation

**Before sealed (Java 8):** Team adds `WalletPayment` class. Nightly job's `if/else` chain has no branch — silently skips wallet transactions. Finance discovers discrepancy weeks later.

**After sealed (17+):** `PaymentMethod` is sealed. Adding `Wallet` without updating `permits` clause and all switches → **compile error**.

### Production scenario: sealed hierarchy across modules (JPMS)

**Problem.** `sealed interface Event permits OrderEvent` in module `domain`, but `OrderEvent` in module `api` — compilation fails.

**Cause.** Sealed permits require classes in same module or explicitly exported packages.

**Fix.** Co-locate sealed root and permitted types in one module, or use `non-sealed` bridge carefully.

## 6. Pattern Matching

### `instanceof` pattern matching (Java 16+, finalized 17)

Eliminates cast boilerplate:

```java
// Before
if (obj instanceof String) {
    String s = (String) obj;
    System.out.println(s.toUpperCase());
}

// After
if (obj instanceof String s) {
    System.out.println(s.toUpperCase());
}
```

The pattern variable `s` is in scope where the compiler can prove `obj` is a `String`.

### Scope rules (flow sensitivity)

```java
if (obj instanceof String s && s.length() > 5) { ... }  // OK
if (obj instanceof String s) {
    // s in scope here
} else {
    // s NOT in scope here
}
```

### Null handling

`instanceof` returns `false` for `null` — no NPE:

```java
if (obj instanceof String s) { ... }  // false if obj is null, block skipped
```

### Record patterns (Java 21)

Destructure records directly in `instanceof` and `switch`:

```java
record Point(int x, int y) {}
record Line(Point start, Point end) {}

static String classify(Object shape) {
    if (shape instanceof Line(Point(var x1, var y1), Point(var x2, var y2)) && x1 == x2) {
        return "vertical line";
    }
    if (shape instanceof Point p) {
        return "point at " + p.x() + "," + p.y();
    }
    return "unknown";
}
```

### Type patterns in switch (see Section 7)

Pattern matching for `switch` combines type tests, deconstruction, and guards (`when`).

### Guarded patterns

```java
static String grade(Object score) {
    return switch (score) {
        case Integer i when i >= 90 -> "A";
        case Integer i when i >= 80 -> "B";
        case Integer i -> "C";
        case null -> "N/A";
        default -> "?";
    };
}
```

### Production scenario: instanceof chain in message dispatcher

**Before:**

```java
void handle(Event e) {
    if (e instanceof OrderPlaced) {
        OrderPlaced op = (OrderPlaced) e;
        handleOrderPlaced(op.orderId(), op.amount());
    } else if (e instanceof OrderCancelled) {
        ...
    }
}
```

**After (sealed + patterns):**

```java
void handle(Event e) {
    switch (e) {
        case OrderPlaced(var id, var amount, var at) -> handleOrderPlaced(id, amount);
        case OrderCancelled(var id, var reason) -> handleCancelled(id, reason);
    }
}
```

Fewer casts, compiler-checked exhaustiveness, clearer dispatch table.

### Production scenario: dominance and compile errors

**Problem.** `case String s` before `case CharSequence cs` — compile error (String dominates CharSequence).

**Fix.** Order cases from **most specific** to **most general**, or use separate switch chains.

## 7. Switch Expressions

### Switch statement vs expression

**Statement** (classic): can fall through, no return value.

**Expression** (Java 14+): every branch must produce a value (or `throw`); no fall-through.

```java
// Expression form
String label = switch (day) {
    case MONDAY, FRIDAY -> "weekday";
    case SATURDAY, SUNDAY -> "weekend";
    default -> "midweek";
};

// With yield (block in arrow case)
int days = switch (month) {
    case JANUARY, MARCH, MAY -> 31;
    case FEBRUARY -> {
        int y = Year.now().getValue();
        yield Year.isLeap(y) ? 29 : 28;
    }
    default -> 30;
};
```

### Exhaustiveness with enums and sealed types

When switching on an **enum** or **sealed** type, omitting a case is a **compile error** (if all cases not covered and no default).

```java
enum Status { ACTIVE, INACTIVE, DELETED }

// Compile error — missing DELETED
String s = switch (status) {
    case ACTIVE -> "ok";
    case INACTIVE -> "off";
};
```

### Null in switch (Java 21)

`switch` throws `NullPointerException` if selector is null — unless you handle `case null`:

```java
String r = switch (maybe) {
    case null -> "none";
    case "a" -> "alpha";
    default -> "other";
};
```

### Pattern matching switch (finalized 21)

```java
static String format(PaymentMethod pm) {
    return switch (pm) {
        case CreditCard(var last4) -> "Card *" + last4;
        case Upi(var vpa) -> "UPI " + vpa;
        case NetBanking(var bank) -> bank;
    };
}
```

### Production scenario: switch expression in REST mapper

Map domain sealed hierarchy to API response without Visitor boilerplate:

```java
public ApiResponse toApi(DomainEvent e) {
    return switch (e) {
        case UserCreated(var id, var email) -> new ApiResponse("user.created", Map.of("id", id, "email", email));
        case UserDeleted(var id) -> new ApiResponse("user.deleted", Map.of("id", id));
    };
}
```

### Production scenario: forgetting `yield` in block case

**Problem.** Compile error: "switch expression does not yield a value."

```java
int x = switch (n) {
    case 1 -> { System.out.println("one"); }  // block without yield
    default -> 0;
};
```

**Fix.** Add `yield 1;` or use arrow `case 1 -> 1`.

## 8. Text Blocks

### Syntax (Java 15+)

Multi-line string literals with automatic indentation handling:

```java
String json = """
    {
        "name": "Sanjay",
        "role": "engineer"
    }
    """;
```

Opening `"""` must be followed by line terminator. Closing `"""` position determines incidental indentation stripped from every line.

### Escapes and formatting

- `\` at end of line — suppress newline (line continuation)
- `\s` — preserve trailing space (Java 15+)
- `String.formatted` / `formatted()` — interpolate:

```java
String name = "World";
String msg = """
    Hello, %s!
    """.formatted(name);
```

### SQL in repositories

```java
private static final String FIND_PENDING = """
    SELECT o.id, o.total, c.name
    FROM orders o
    JOIN customers c ON o.customer_id = c.id
    WHERE o.status = 'PENDING'
      AND o.created_at > :since
    """;
```

### JSON test fixtures

```java
String fixture = """
    {
        "orderId": "ord-123",
        "lines": [
            {"sku": "A1", "qty": 2}
        ]
    }
    """;
Order order = mapper.readValue(fixture, Order.class);
```

### Production scenario: accidental indentation in SQL

**Problem.** Text block includes leading spaces from method body indentation — SQL sent to DB has weird leading whitespace.

**Cause.** Closing `"""` aligned with code indent strips matching spaces from all lines — but misaligned closing delimiter strips wrong amount.

**Fix.** Align closing `"""` with content left edge, or use `.stripIndent()` explicitly:

```java
String sql = """
        SELECT id FROM users
        """.stripIndent();
```

### Production scenario: text block in properties vs externalized config

Text blocks are great for **static** SQL/GraphQL in code. Dynamic templates still belong in config stores or template engines — do not embed environment-specific values in text block literals.

### Text blocks vs string concatenation

| Approach | When |
|---|---|
| Text block | Multi-line, readable structure (SQL, JSON, HTML snippets) |
| `+` concatenation | Single line or dynamic pieces |
| Template engine | User-facing emails with complex logic |

## 9. Virtual Threads — Overview

> **Deep dive:** [`java-concurrency.md`](java-concurrency.md) — carrier threads, pinning, schedulers, Spring Boot integration, structured concurrency.

### The problem

Platform (OS) threads are **expensive** (~1 MB stack, kernel scheduling). Traditional thread-per-request models cap at hundreds–low thousands of concurrent requests. Reactive stacks (WebFlux, RxJava) scale I/O but impose callback hell.

### Virtual threads (Project Loom, finalized Java 21)

**Virtual threads** are JVM-managed, lightweight threads — mount on **carrier** platform threads. Blocking I/O **parks** the virtual thread without blocking the carrier.

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<String>> futures = new ArrayList<>();
    for (String url : urls) {
        futures.add(executor.submit(() -> httpClient.get(url)));
    }
    for (Future<String> f : futures) {
        process(f.get());
    }
}
```

Millions of virtual threads are feasible. Code stays **blocking and readable**.

### Spring Boot 3.2+

```properties
spring.threads.virtual.enabled=true
```

Tomcat/Jetty dispatch each request on a virtual thread. Blocking JDBC and `RestTemplate` calls no longer exhaust a small platform thread pool.

### When virtual threads help

| Workload | Benefit |
|---|---|
| I/O-bound (HTTP, DB, messaging) | High — massive concurrency with simple code |
| CPU-bound computation | Low — use platform threads or `ForkJoinPool` |
| Heavy `synchronized` + blocking | Caution — pinning (see concurrency note) |
| Native code / JNI blocking | May pin carrier |

### When **not** to use virtual threads

- CPU-saturated work — more threads ≠ more throughput
- Thread-local heavy code without migration to `ScopedValue`
- Libraries that pool platform threads assuming thread == request isolation at OS level (rare)

### Virtual threads vs reactive

| | Virtual threads | WebFlux / reactive |
|---|---|---|
| Code style | Blocking, imperative | Functional, composable |
| Backpressure | Manual / bounded queues | Built into reactive streams |
| Ecosystem fit | Existing JDBC, blocking clients | Non-blocking drivers required |
| Debugging | Standard stack traces | Async stack trace pain |

**Interview answer:** "For typical Spring MVC + JDBC microservices, virtual threads are the default choice in 2024+. Reach for reactive when you need fine-grained backpressure or are already on non-blocking drivers end-to-end."

### Structured concurrency (preview in 21)

Treat related tasks as one unit — failure cancels siblings. See [`java-concurrency.md`](java-concurrency.md).

```java
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Supplier<Inventory> inv = scope.fork(() -> inventoryClient.check(sku));
    Supplier<Price> price = scope.fork(() -> pricingClient.get(sku));
    scope.join().throwIfFailed();
    return new CheckoutResult(inv.get(), price.get());
}
```

### Scoped values (preview in 21)

Immutable request context alternative to `ThreadLocal` — designed for millions of virtual threads. See concurrency note for MDC/trace propagation patterns.

### Production scenario: 50k concurrent HTTP fan-out

**Before:** Thread pool of 200 → queue grows, timeouts cascade.

**After:** Virtual thread per request → each blocks independently on I/O; carriers reused efficiently.

**Measure:** Compare p99 latency and CPU under load — virtual threads are not free; scheduler and pinning matter.

## 10. Sequenced Collections

> **Collection internals and iteration contracts:** [`java-collections.md`](java-collections.md)

### The gap before Java 21

`List` had indexed access but no `getFirst()`/`getLast()`. `LinkedHashSet` and `LinkedHashMap` had encounter order but no unified API for "first inserted" or "reversed view." Developers used `iterator().next()`, `list.get(0)`, or awkward deque workarounds.

### New interfaces (JEP 431, Java 21)

| Interface | Extends | Key methods |
|---|---|---|
| `SequencedCollection<E>` | `Collection<E>` | `getFirst()`, `getLast()`, `addFirst()`, `addLast()`, `reversed()` |
| `SequencedSet<E>` | `Set<E>, SequencedCollection<E>` | same |
| `SequencedMap<K,V>` | `Map<K,V>` | `firstEntry()`, `lastEntry()`, `pollFirstEntry()`, `pollLastEntry()`, `reversed()` |

### Implementations

- `List`, `Deque` implementations → `SequencedCollection`
- `LinkedHashSet` → `SequencedSet`
- `LinkedHashMap`, `TreeMap` → `SequencedMap`

### Examples

```java
List<String> list = new ArrayList<>(List.of("a", "b", "c"));
String first = list.getFirst();   // "a"
String last = list.getLast();     // "c"
List<String> rev = list.reversed(); // view, not copy — mutating list affects view

LinkedHashMap<String, Integer> map = new LinkedHashMap<>();
map.put("x", 1);
map.put("y", 2);
Map.Entry<String, Integer> oldest = map.firstEntry();
```

### `reversed()` returns a view

Mutations through `reversed()` affect the backing collection. For a snapshot, copy first:

```java
List<String> snapshot = List.copyOf(list.reversed());
```

### Production scenario: LRU-ish access without LinkedHashMap boilerplate

**Before:**

```java
Map.Entry<K, V> eldest = map.entrySet().iterator().next(); // unclear intent
```

**After:**

```java
Map.Entry<K, V> eldest = map.firstEntry();
Map.Entry<K, V> newest = map.lastEntry();
```

Clearer intent in audit logs and undo stacks.

### Production scenario: `getFirst()` on empty list

Throws `NoSuchElementException` — same as `Deque.getFirst()`. Use `isEmpty()` check or:

```java
var first = list.isEmpty() ? Optional.<String>empty() : Optional.of(list.getFirst());
```

### Interaction with immutable lists

```java
List<String> immutable = List.of("a", "b");
immutable.getFirst();  // OK
immutable.addFirst("z"); // UnsupportedOperationException
```

## 12. Java Platform Module System (JPMS)

### Why modules exist (Java 9)

JPMS (`module-info.java`) addresses:
- **Strong encapsulation** — hide internal packages
- **Reliable configuration** — explicit dependencies
- **Smaller runtime** — `jlink` custom images

### Module descriptor

```java
module com.example.app {
    requires com.example.db;
    requires transitive com.example.api;
    exports com.example.app.api;
    opens com.example.app.dto to com.fasterxml.jackson.databind;
}
```

### Named vs unnamed module

| Module type | Description |
|---|---|
| Named | Has `module-info.java` |
| Automatic | JAR on module path without descriptor — exports all, requires all |
| Unnamed | Classpath JARs — legacy behavior |

### Classpath vs module path

```
Classpath (unnamed module):  all packages "visible", weak encapsulation
Module path:                 explicit requires/exports, strong encapsulation
```

**Most Spring Boot apps still run on classpath** — fat JARs are unnamed modules. Full modularization is rare except libraries and `jlink` deployments.

### `jlink` — custom runtime images

```bash
jlink --add-modules java.base,java.logging,com.example.app \
      --output runtime-image \
      --strip-debug --compress=2
```

Produces a minimal JVM — useful for containers and CLI tools.

### JPMS and reflection

Frameworks (Spring, Hibernate, Jackson) need deep reflection. Solutions:
- `opens package to module;`
- `--add-opens java.base/java.lang=ALL-UNNAMED` (migration crutch)
- Spring Boot 3 on 17+ documents required opens

### Production scenario: `IllegalAccessError` after modularizing library

**Problem.** Internal package `com.lib.internal` used by consumers via reflection — now hidden.

**Fix.** Export/open explicitly, or keep library on classpath as automatic module with documented illegal access flags (temporary).

### Production scenario: split packages

Two JARs defining `com.foo.util` — module system rejects merge.

**Fix.** Rename packages or merge JARs — no workaround except classpath (unnamed).

### Senior guidance

- **Libraries:** consider multi-release + module descriptor for public API
- **Microservices:** classpath fat JAR is fine; focus on JDK version and `--add-opens` audit for 17+
- **CLI/edge:** `jlink` images reduce attack surface and image size

## 15. Performance Across Releases

### GC evolution

| GC | Era | Character |
|---|---|---|
| Parallel | Pre-9 default | Throughput, stop-the-world |
| G1 | 9+ default | Balanced, regional |
| ZGC | 15 exp → 21 generational | Low latency, large heaps |
| Shenandoah | Red Hat/OpenJDK | Low pause alternative |

**Java 21 Generational ZGC:** young/old separation — better CPU efficiency for typical allocation patterns.

```bash
# Large heap, latency-sensitive
java -XX:+UseZGC -Xmx32g -jar app.jar
```

### JIT compiler improvements

Each release improves C2 inlining, escape analysis, and intrinsic methods. **Upgrading JDK without code changes** often yields 5–15% throughput gains in benchmarks — measure your workload.

### Startup time

- **CDS (Class Data Sharing):** build shared archive for faster startup
- **Spring AOT / GraalVM Native Image:** separate path — instant startup, different tradeoffs

```bash
java -Xshare:dump -XX:SharedArchiveFile=app.jsa -cp app.jar
java -Xshare:on -XX:SharedArchiveFile=app.jsa -jar app.jar
```

### Container awareness

JDK 10+ respects cgroup memory/CPU limits for default heap and GC threads. **Always set container limits** and verify JVM sees them:

```bash
java -XX:+PrintFlagsFinal -version | grep ActiveProcessorCount
```

### Lambda and stream performance

Lambdas via invokedynamic are efficient after warmup. Streams add abstraction overhead — hot paths may still favor indexed `for` loops. See [`java-streams.md`](java-streams.md) Section 18.

### Virtual threads and throughput

Virtual threads improve **scalability** (concurrency), not single-request CPU speed. CPU-bound work does not get faster with virtual threads.

### Production scenario: G1 pause regression after upgrade

**Problem.** p99 latency worse on 17 than 11.

**Investigation:** JFR compare — maybe heap too small, humongous allocations, or changed default GC tuning.

**Fix:** Explicit `-Xms`/`-Xmx`, G1 region size tuning, or try ZGC for large heap.

### Production scenario: metaspace OOM after upgrade

**Cause.** More classes loaded (framework upgrade, more lambdas synthetic classes, or classloader leak).

**Fix:** `-XX:MaxMetaspaceSize`, fix classloader leaks, analyze with `jcmd VM.classloader_stats`.

### PermGen → Metaspace (Java 8)

Java 8 removed PermGen — metaspace uses native memory. Hot redeploy classloader leaks now manifest as native OOM, not `PermGen space`.

## 18. Production Debugging Playbook

### Symptom → cause → action

| Symptom | Likely cause | First action |
|---|---|---|
| `UnsupportedClassVersionError` | Jar compiled for newer JDK | `javap -verbose Foo.class \| grep major` |
| `InaccessibleObjectException` | Illegal reflective access on 17+ | Upgrade lib or `--add-opens` (temp) |
| `ClassNotFoundException: javax.xml.bind` | JAXB removed from JDK 11+ | Add Jakarta JAXB deps |
| `NoSuchMethodError` / `NoClassDefFoundError` at runtime | Dependency conflict / wrong JDK | `mvn dependency:tree`, verify CI JDK |
| Thread pool exhausted (pre-21) | Blocking I/O on platform threads | Virtual threads or larger pool + queue |
| Virtual thread pinning | `synchronized` + block on carrier | JFR `jdk.VirtualThreadPinned`, refactor lock |
| `IllegalStateException: stream already operated` | Stream reuse | [`java-streams.md`](java-streams.md) |
| Metaspace / native OOM | Classloader leak | Heap dump + classloader stats |
| GC pause SLA breach | Wrong GC / heap sizing | JFR GC events, try ZGC |
| Flaky tests after upgrade | Mockito/bytecode timing | Upgrade test stack, deterministic clocks |

### JFR one-liner (production-safe)

```bash
java -XX:StartFlightRecording=duration=120s,filename=rec.jfr,settings=profile \
     -jar app.jar
```

Open in JDK Mission Control or `jfr print rec.jfr`.

### Useful diagnostic commands

```bash
jcmd <pid> VM.version
jcmd <pid> Thread.print
jcmd <pid> GC.heap_info
jcmd <pid> VM.classloader_stats
jfr summary rec.jfr
```

### Logging JDK migration issues

Add structured fields: `jdk.version`, `vm.name`, `spring.boot.version`. Correlate errors post-cutover.

### Production scenario: intermittent `InaccessibleObjectException` only in prod

**Cause.** Different JVM args than CI — prod missing `--add-opens` that dev added manually.

**Fix.** Document all JVM flags in infrastructure-as-code; remove opens by fixing dependency versions.

### Production scenario: virtual thread deadlock

**Cause.** Pinning + carrier pool starvation, or classic lock ordering deadlock unchanged by virtual threads.

**Fix.** JFR pinning events; thread dump shows virtual vs carrier; refactor `synchronized` to `ReentrantLock` if needed (see [`java-concurrency.md`](java-concurrency.md)).

### Production scenario: class file version mismatch in shaded JAR

**Cause.** Shade plugin bundled dependency compiled for Java 21 into app targeting 17.

**Fix.** Enforce dependency bytecode level; use enforcer + animal-sniffer.

## 19. Quick Decision Matrix

### Language feature selection

| Need | Use | Avoid |
|---|---|---|
| Pass behavior as argument | Lambda / method ref | Anonymous class (verbose) |
| Immutable DTO | `record` | Mutable Lombok `@Data` for events |
| Fixed type hierarchy | `sealed` + records | Open inheritance + Visitor |
| Multi-line SQL/JSON | Text block | Concatenated strings |
| Local type obvious from RHS | `var` | `var` hiding important type |
| Exhaustive dispatch | `switch` on sealed type | Long `if/else instanceof` |
| Optional return | `Optional<T>` return | `null` or Optional field |
| Many concurrent blocking calls | Virtual threads | Bigger platform pool only |
| CPU-bound parallel | `ForkJoinPool` / executor | `parallelStream()` on small data |
| Ordered collection ends | `getFirst()`/`getLast()` | `get(0)`/iterator hacks |

### JDK version selection (2025+)

| Situation | Target |
|---|---|
| Greenfield microservice | **21 LTS** |
| Spring Boot 3.x | **17 minimum**, prefer **21** |
| Legacy Spring Boot 2.x | **11** (plan 17 migration) |
| Android / special constraints | Check toolchain — often not server JDK |
| Library published to Maven Central | Multi-release JAR; bytecode baseline 11 or 17 |

| From | To | Urgency driver |
|---|---|---|
| 8 | 11 | Security EOL, JAXB break |

## Practice Questions & Answers

<details class="qa-item">
<summary>Q1. Why are lambdas not implemented as anonymous inner classes?</summary>

The compiler uses `invokedynamic` and `LambdaMetafactory` to generate synthetic classes at runtime. This avoids one `.class` file per lambda, enables better inlining by the JIT, and separates lambda metafactory logic from anonymous class bytecode bloat.

</details>

<details class="qa-item">
<summary>Q2. What is the difference between `var` and `Object`?</summary>

`var` is compile-time inference — the variable has a specific inferred type (e.g., `ArrayList<String>`). `Object` erases to the root type and loses API (no `add` without cast). `var` is not dynamic typing.

</details>

<details class="qa-item">
<summary>Q3. Can a record implement an interface and add methods?</summary>

Yes. Records can implement interfaces, define instance/static methods, and use compact constructors for validation. They cannot extend classes (implicitly extend `Record`).

</details>

<details class="qa-item">
<summary>Q4. What happens if you add a new permitted subclass to a sealed interface but forget to update switch?</summary>

The compiler reports a non-exhaustive switch error (when switching on the sealed type without `default`). This is the primary production benefit — missing cases become compile failures, not runtime bugs.

</details>

<details class="qa-item">
<summary>Q5. When should you use `default` in a switch on a sealed type?</summary>

Rarely. If all permitted subtypes are covered, `default` is unreachable. Use `default` only when switching on non-sealed types, primitives with ranges, or `Object` receivers.

</details>

<details class="qa-item">
<summary>Q6. How do text blocks handle indentation?</summary>

The compiler strips incidental indentation based on the position of the closing `"""`. Align the closing delimiter with the least-indented content line. Use `\s` to preserve trailing spaces.

</details>

<details class="qa-item">
<summary>Q7. Virtual threads vs platform threads — one-sentence distinction?</summary>

Platform threads map 1:1 to OS threads; virtual threads are JVM-scheduled and mount on a small pool of carrier platform threads, making blocking I/O cheap at massive scale.

</details>

<details class="qa-item">
<summary>Q8. Do virtual threads help CPU-bound workloads?</summary>

No. CPU-bound work still consumes CPU cores. Additional virtual threads beyond core count add scheduling overhead without throughput gain. Use appropriate pool sizing for CPU work.

</details>

<details class="qa-item">
<summary>Q9. What is `list.reversed()` — copy or view?</summary>

A **view** backed by the original list. Changes to either affect the other. For an independent copy, use `List.copyOf(list.reversed())` or `new ArrayList<>(list).reversed()` patterns.

</details>

<details class="qa-item">
<summary>Q10. Why was JAXB removed from the JDK in 11?</summary>

Java EE modules were decoupled from the JDK (Jakarta transition). XML binding belongs as an explicit application dependency, not bundled in the platform.

</details>

<details class="qa-item">
<summary>Q11. What is `--release 21` vs `-source 21 -target 21`?</summary>

`--release 21` sets source, target, and **boot classpath** to the Java 21 API surface — preventing accidental use of APIs that exist only on the newer JDK used to compile. Prefer `--release` in builds.

</details>

<details class="qa-item">
<summary>Q12. Name three Java 11 APIs that reduce third-party dependencies.</summary>

`HttpClient` (HTTP/2), `String.strip`/`isBlank`/`lines`, and `Files.readString`/`writeString` — each replaces common Apache Commons / OkHttp / Guava usage for simple cases.

</details>

<details class="qa-item">
<summary>Q13. What is strong encapsulation in Java 17?</summary>

JDK internal packages (`sun.*`, `jdk.internal.*`) are not accessible via reflection by default. Illegal access throws `InaccessibleObjectException` unless exported/opened or `--add-opens` is used.

</details>

<details class="qa-item">
<summary>Q14. Records and JPA — recommended?</summary>

Generally **no** for entities. JPA needs mutable state, lazy loading proxies, and no-arg constructors. Records fit event DTOs, API responses, and immutable value types. Use classes or Kotlin for entities.

</details>

<details class="qa-item">
<summary>Q15. Pattern matching `instanceof` — is null safe?</summary>

Yes. `null instanceof String s` evaluates to `false`; the block is skipped without NPE.

</details>

<details class="qa-item">
<summary>Q16. Switch expression — what happens if a case is missing for an enum?</summary>

Compile-time error: switch expression not exhaustive. Add the missing enum constant case or a `default` (if acceptable for your domain).

</details>

<details class="qa-item">
<summary>Q17. How do you enable preview features?</summary>

Compile: `javac --enable-preview --release 21 ...`
Run: `java --enable-preview ...`
Do not use in production without explicit organizational approval.

</details>

<details class="qa-item">
<summary>Q18. What is Generational ZGC in Java 21?</summary>

ZGC with separate young/old generations, reducing GC CPU overhead and improving throughput vs single-generation ZGC while maintaining low pause times on large heaps.

</details>

<details class="qa-item">
<summary>Q19. CompletableFuture vs virtual threads for parallel HTTP calls?</summary>

Both work. Virtual threads allow simple blocking code per task. `CompletableFuture` composes async pipelines explicitly. For Spring MVC + blocking clients, virtual threads are usually simpler. See [`java-concurrency.md`](java-concurrency.md).

</details>

<details class="qa-item">
<summary>Q20. What tool finds deprecated API usage before migration?</summary>

`jdeprscan --release 21 --class-path app.jar your.packages`

</details>

<details class="qa-item">
<summary>Q21. Why might parallelStream make things slower?</summary>

Split overhead, small data sets, poor spliterator (e.g., `LinkedList`), blocking operations on common pool, or non-associative combiners. See [`java-streams.md`](java-streams.md) Section 14.

</details>

<details class="qa-item">
<summary>Q22. Sealed class permits across modules — requirement?</summary>

Permitted classes must be in the same module as the sealed type, or the sealed type's module must read and export/open appropriately. Cross-module sealed hierarchies need careful JPMS design.

</details>

<details class="qa-item">
<summary>Q23. `Optional` as field type — why discouraged?</summary>

`Optional` was designed for return types to signal absence. As fields/parameters it adds serialization, JPA, and memory overhead without API clarity. Use nullable fields with documentation or validation instead.

</details>

<details class="qa-item">
<summary>Q24. Java 8 PermGen vs Metaspace — production impact?</summary>

PermGen was a fixed JVM heap region for class metadata — hot redeploys caused `OutOfMemoryError: PermGen space`. Metaspace uses native memory and grows dynamically — different failure mode (native OOM) if classloaders leak.

</details>

<details class="qa-item">
<summary>Q25. Spring Boot 3 minimum Java version?</summary>

Java **17**. Spring Boot 3.2+ adds first-class virtual thread support on Java **21**.

</details>

<details class="qa-item">
<summary>Q26. Record compact constructor — when does validation run?</summary>

Before field assignment. Assignments to components in compact constructor body are optional — the compiler assigns parameters to fields after the compact constructor logic.

</details>

<details class="qa-item">
<summary>Q27. What is pinning in virtual threads?</summary>

When a virtual thread blocks in a way that holds its carrier platform thread (e.g., some `synchronized` + native blocking scenarios), preventing carrier reuse. JFR event `jdk.VirtualThreadPinned` helps diagnose.

</details>

<details class="qa-item">
<summary>Q28. `Map.of` vs `Map.copyOf`?</summary>

`Map.of` creates immutable map from known entries (max 10 pairs in overloads). `Map.copyOf(map)` creates unmodifiable copy from any map — throws if source has duplicate keys during copy.

</details>

<details class="qa-item">
<summary>Q29. When to choose sealed interface over enum?</summary>

When each variant carries different data fields (records as cases). Enums suit fixed singleton constants without per-case payload diversity.

</details>

<details class="qa-item">
<summary>Q30. LTS migration — Big Bang vs strangler?</summary>

**Strangler:** migrate service-by-service with CI on target JDK — lower blast radius. **Big Bang:** single cutover — only when test coverage and rollback images are exceptional. Senior teams prefer strangler with canaries.

</details>

<details class="qa-item">
<summary>Q31. Where do Stream API details live in this notes set?</summary>

[`java-streams.md`](java-streams.md) — pipelines, collectors, parallel streams, Optional, debugging. This note only references streams where relevant to version features.

</details>

<details class="qa-item">
<summary>Q32. `HttpClient` — sync vs async send?</summary>

`send()` blocks (use on virtual threads for scale). `sendAsync()` returns `CompletableFuture<HttpResponse<T>>` for non-blocking style without virtual threads.

</details>

<details class="qa-item">
<summary>Q33. What changed with `javax` → `jakarta` in Java EE migration?</summary>

Namespace rename for Servlet, JPA, Validation, etc. (`javax.persistence` → `jakarta.persistence`). Required for Spring Boot 3 / Tomcat 10+. Not a JDK change but mandatory in 11→17 ecosystem upgrades.

</details>

<details class="qa-item">
<summary>Q34. jlink use case in microservices?</summary>

Custom runtime images with only required modules — smaller container images and reduced attack surface. More common for CLI/edge than typical Spring Boot fat JARs.

</details>

<details class="qa-item">
<summary>Q35. Decision: WebFlux or virtual threads for I/O service?</summary>

**Virtual threads** if stack is blocking JDBC/HTTP and team knows Spring MVC. **WebFlux** if already on reactive drivers and need backpressure-native pipelines. Hybrid migrations are costly — pick one model per service.

</details>
