## JAVA 8 (March 2014) — The Functional Revolution

### 1. Lambda Expressions
Anonymous functions — replace verbose anonymous inner classes.

```java
// Before
Comparator<String> c = new Comparator<String>() {
    public int compare(String a, String b) { return a.length() - b.length(); }
};
// After
Comparator<String> c = (a, b) -> a.length() - b.length();
```

**Production scenario:** In an e-commerce order service, sorting a `List<Order>` by `orderDate` descending for a "recent orders" API:
```java
orders.sort((o1, o2) -> o2.getOrderDate().compareTo(o1.getOrderDate()));
```
**Answer/why it matters:** Reduces boilerplate in event listeners, comparators, and callback-heavy code (Spring `RowMapper`, `Runnable` for thread pools, etc.), making code diffs smaller and intent clearer in code review.

### 2. Functional Interfaces
`Function<T,R>`, `Predicate<T>`, `Supplier<T>`, `Consumer<T>`, `BiFunction`, etc. — interfaces with exactly one abstract method, target types for lambdas.

**Production scenario:** A validation pipeline in a payment service:
```java
Predicate<Payment> isValidAmount = p -> p.getAmount().compareTo(BigDecimal.ZERO) > 0;
Predicate<Payment> isKnownCurrency = p -> supportedCurrencies.contains(p.getCurrency());
Predicate<Payment> isValid = isValidAmount.and(isKnownCurrency);
if (!isValid.test(payment)) throw new InvalidPaymentException();
```
**Answer:** Composable business rules without writing a new interface per rule — critical in rule-engine-style services (fraud checks, discount eligibility).

### 3. Stream API
Declarative processing of collections — filter/map/reduce, supports parallelism.

**Production scenario:** Aggregating daily transaction totals per merchant from a `List<Transaction>` of 2 million records nightly batch job:
```java
Map<String, BigDecimal> totalsByMerchant = transactions.stream()
    .collect(Collectors.groupingBy(Transaction::getMerchantId,
             Collectors.reducing(BigDecimal.ZERO, Transaction::getAmount, BigDecimal::add)));
```
**Answer:** Readable, and `.parallelStream()` can be used for CPU-bound batch jobs on multi-core machines — but in production, avoid parallelStream on shared `ForkJoinPool.commonPool()` when a web server is also using it for other tasks (thread starvation risk). Prefer a custom `ForkJoinPool` for batch jobs.

### 4. Default & Static Methods in Interfaces
Allows interface evolution without breaking implementers.

**Production scenario:** Spring Data JPA repositories add default methods like `findAll(Sort sort)` without forcing every custom repository implementation to change. Internally, this is how Java itself added `Collection.stream()` to every existing `Collection` implementation without breaking third-party code.

### 5. Optional<T>
Explicit container for possibly-absent values — reduces `NullPointerException`.

**Production scenario:** A user profile service:
```java
public Optional<Address> getPrimaryAddress(User user) {
    return Optional.ofNullable(user.getAddresses())
        .flatMap(list -> list.stream().filter(Address::isPrimary).findFirst());
}
// Caller
String city = getPrimaryAddress(user).map(Address::getCity).orElse("Unknown");
```
**Answer:** Forces callers to explicitly handle the empty case at compile-time intent level. **Anti-pattern to call out in interviews:** never use `Optional` as a field type or method parameter — only as a return type.

### 6. New Date/Time API (`java.time`)
Immutable, thread-safe replacement for `Date`/`Calendar` (which had mutable state bugs and were not thread-safe).

**Production scenario:** A booking system computing SLA deadlines across timezones:
```java
ZonedDateTime bookingTime = ZonedDateTime.now(ZoneId.of("Asia/Kolkata"));
ZonedDateTime slaDeadline = bookingTime.plusHours(24).withZoneSameInstant(ZoneId.of("UTC"));
```
**Answer:** Old `Calendar`/`SimpleDateFormat` were not thread-safe — a shared static `SimpleDateFormat` in a multi-threaded servlet was a classic production bug (corrupted dates under load). `DateTimeFormatter` in `java.time` is thread-safe and can be a shared static instance.

### 7. Method References
Shorthand for lambdas that just call an existing method: `Class::staticMethod`, `object::instanceMethod`, `Class::instanceMethod`, `Class::new`.
```java
list.forEach(System.out::println);
List<User> users = ids.stream().map(userRepository::findById).toList();
```

### 8. CompletableFuture
Composable async programming, successor to `Future`.

**Production scenario:** A checkout service that calls inventory, pricing, and shipping microservices in parallel and combines results:
```java
CompletableFuture<Inventory> inv = CompletableFuture.supplyAsync(() -> inventoryClient.check(sku), executor);
CompletableFuture<Price> price = CompletableFuture.supplyAsync(() -> pricingClient.get(sku), executor);
CompletableFuture<CheckoutResult> result = inv.thenCombine(price, CheckoutResult::new)
    .exceptionally(ex -> CheckoutResult.failed(ex.getMessage()));
```
**Answer:** Cuts total latency from sum-of-calls to max-of-calls. Always supply a dedicated `Executor` in production — never rely on the default `ForkJoinPool.commonPool()` for I/O-bound calls, since it's sized for CPU-bound work and shared JVM-wide.

### 9. Nashorn JavaScript Engine
Embedded JS engine (later deprecated in 11, removed in 15). Rarely used in production; mention only if asked about deprecated features.

### 10. PermGen Removed → Metaspace
PermGen (fixed-size, caused `OutOfMemoryError: PermGen space` from excessive class loading, common in app servers doing hot redeploys) replaced by Metaspace (native memory, grows dynamically).
**Production relevance:** Reduced a very common class of OOM crashes in Tomcat/JBoss apps that redeployed frequently.

## JAVA 11 (Sept 2018, LTS)

### 1. `var` for Local Variables (actually Java 10, but first LTS to carry it)
Local-variable type inference — compiler infers type, still statically typed (not dynamic typing).
```java
var orders = new ArrayList<Order>();
var connection = dataSource.getConnection();
```
**Production guidance (common interview trap):** Use `var` only when the right-hand side makes the type obvious. Avoid `var result = service.process();` where the type isn't clear from context — hurts readability in code review.

### 2. New String Methods
`isBlank()`, `strip()`/`stripLeading()`/`stripTrailing()` (Unicode-aware, unlike `trim()`), `lines()`, `repeat(n)`.

**Production scenario:** Parsing a multi-line CSV-like config uploaded by users with mixed whitespace (including non-ASCII spaces from copy-pasted Excel data):
```java
config.lines()
      .map(String::strip)
      .filter(line -> !line.isBlank())
      .forEach(this::parseLine);
```
**Answer:** `trim()` only strips ASCII ≤ `\u0020`; `strip()` uses `Character.isWhitespace`, correctly handling Unicode whitespace — matters when ingesting user-uploaded files from various locales.

### 3. `java.net.http.HttpClient` (Standardized)
Replaces `HttpURLConnection` and third-party libs like Apache HttpClient for many use cases. Supports HTTP/2, WebSocket, sync and async.

**Production scenario:** Calling a downstream REST API with async, non-blocking I/O in a high-throughput service:
```java
HttpClient client = HttpClient.newBuilder().version(HttpClient.Version.HTTP_2).build();
HttpRequest request = HttpRequest.newBuilder(URI.create(url)).GET().timeout(Duration.ofSeconds(5)).build();
client.sendAsync(request, HttpResponse.BodyHandlers.ofString())
      .thenApply(HttpResponse::body)
      .thenAccept(this::processResponse);
```
**Answer:** Removes a common third-party dependency (Apache HttpClient/OkHttp) for simple cases, reduces jar bloat, and gives built-in HTTP/2 multiplexing — fewer TCP connections to downstream services under load.

### 4. `Files.readString()` / `Files.writeString()`
One-liners for whole-file text I/O, replacing verbose `BufferedReader` boilerplate for small config/property files.
```java
String content = Files.readString(Path.of("/etc/app/config.json"));
```

### 5. Local-Variable Syntax for Lambda Parameters
```java
list.stream().map((var x) -> x.getName());
```
Mainly useful so you can annotate lambda parameters (e.g., `@Nullable`), otherwise rarely needed.

### 6. Single-File Source-Code Execution
`java HelloWorld.java` runs a `.java` file directly without a separate `javac` step.
**Production relevance:** Useful for quick scripts/utilities and CI throwaway checks, not for deployed services.

### 7. Removal of Java EE & CORBA Modules
`java.xml.bind` (JAXB), `java.xml.ws` (JAX-WS), `java.corba`, `java.activation` removed from the JDK.
**Production scenario:** Legacy Spring/JEE apps using JAXB for XML marshalling broke on upgrade to 11 with `ClassNotFoundException: javax.xml.bind.JAXBException`.
**Answer:** Add `jaxb-api` + `jaxb-runtime` as explicit Maven/Gradle dependencies before migrating — a very common real-world Java 8→11 migration blocker asked about in interviews.

### 8. Flight Recorder (JFR) Open-Sourced
Low-overhead (~1-2%) production profiling built into the JVM, previously a paid Oracle feature.
**Production scenario:** Diagnosing an intermittent latency spike in production without attaching a heavyweight profiler:
```
java -XX:+FlightRecorder -XX:StartFlightRecording=duration=60s,filename=recording.jfr -jar app.jar
```
Analyze with JDK Mission Control to find GC pauses, lock contention, or slow methods.
**Answer:** This is the standard modern way to profile production JVMs safely — replaces older, riskier `jstack`/heap-dump-only debugging under live traffic.

### 9. Epsilon GC & ZGC (Experimental)
Epsilon = a no-op GC (for measuring pure allocation overhead / ultra-short-lived jobs). ZGC = low-latency GC targeting sub-10ms pause times, aimed at large heaps (production-ready by 15/17).

### 10. Deprecations
Nashorn deprecated; `java.applet` deprecated — signal of the JDK trimming dead weight.

## JAVA 17 (Sept 2021, LTS)

### 1. Sealed Classes/Interfaces (JEP 409)
Restrict which classes can extend/implement a type — controlled inheritance hierarchies.
```java
public sealed interface PaymentMethod permits CreditCard, UPI, NetBanking {}
public final class CreditCard implements PaymentMethod {}
public final class UPI implements PaymentMethod {}
public final class NetBanking implements PaymentMethod {}
```
**Production scenario:** Modeling a fixed set of payment types in a payments platform so the compiler enforces exhaustive handling everywhere `PaymentMethod` is switched on — prevents a new payment type from silently falling through unhandled logic when someone adds `Wallet` later without updating every switch statement.

### 2. Pattern Matching for `switch` (Preview in 17, finalized in 21)
```java
String describe(PaymentMethod pm) {
    return switch (pm) {
        case CreditCard c -> "Card ending " + c.last4();
        case UPI u -> "UPI: " + u.vpa();
        case NetBanking n -> "Bank: " + n.bankName();
    };
}
```
Combined with sealed classes above, the compiler enforces exhaustiveness — no `default` needed, and a compile error if a new subtype is added and not handled.
**Answer (production value):** This directly prevents a whole class of production bugs — "we added a new enum/type and forgot to update the switch in the reconciliation job" — because it becomes a **compile-time error**, not a runtime silent failure.

### 3. Records (Finalized in 16, heavily used from 17)
Immutable data carriers — auto-generates constructor, accessors, `equals()`, `hashCode()`, `toString()`.
```java
public record OrderSummary(String orderId, BigDecimal total, LocalDate date) {}
```
**Production scenario:** DTOs for REST API responses and Kafka event payloads:
```java
public record OrderCreatedEvent(String orderId, String customerId, BigDecimal amount, Instant createdAt) {}
```
**Answer:** Eliminates ~40 lines of Lombok-style boilerplate per DTO, and being immutable by default makes them safe to pass across threads (e.g., Kafka consumer threads) without defensive copying concerns.

### 4. Text Blocks (Finalized in 15)
Multi-line string literals — huge for embedded SQL/JSON.
```java
String sql = """
    SELECT o.id, o.total, c.name
    FROM orders o JOIN customers c ON o.customer_id = c.id
    WHERE o.status = 'PENDING'
    """;
```
**Production scenario:** Native SQL queries in a `JdbcTemplate`-based repository, or JSON test fixtures in integration tests — removes string-concatenation escaping bugs (`\"` everywhere) that previously caused subtle SQL syntax errors.

### 5. Strong Encapsulation of JDK Internals (JEP 403)
`--illegal-access=permit` flag removed; internal APIs (`sun.misc.*`, etc.) are now strongly encapsulated by default.
**Production scenario (major migration pain point):** Libraries like older versions of Mockito, Lombok, or ORM frameworks that used reflection to access internal JDK classes (e.g., `sun.nio.ch.*`) throw `InaccessibleObjectException` on Java 17.
**Answer:** Before migrating a legacy Spring Boot 2.x app to Java 17, audit dependencies for JDK-internal reflection usage; most require upgrading to newer library versions (this is a top real-world Java 11→17 migration checklist item).

### 6. Enhanced Pseudo-Random Number Generators (JEP 356)
New `RandomGenerator` interface, algorithms like `Xoshiro256PlusPlus` — better statistical quality and splittable for parallel streams than legacy `java.util.Random`.
**Production scenario:** Load-testing tools or Monte Carlo risk simulations in a trading system needing many independent parallel random streams:
```java
RandomGenerator rng = RandomGeneratorFactory.of("Xoshiro256PlusPlus").create();
```

### 7. Foreign Function & Memory API (Incubator)
Safer, faster alternative to JNI for calling native code (C libraries) and off-heap memory access. (Finalized later, in Java 22.)
**Production relevance:** Relevant for high-performance systems calling native libraries (e.g., custom compression, crypto) without JNI's boilerplate and unsafety.

### 8. Other 17 Notables
- Deprecation of the Security Manager for removal.
- macOS AArch64 (Apple Silicon) port — native M1/M2 support.
- Context-specific deserialization filters (`ObjectInputFilter`) — security hardening against Java deserialization attacks, a real class of production CVEs (e.g., in older versions of Jackson/Log4j-adjacent ecosystems).

## JAVA 21 (Sept 2023, LTS)

### 1. Virtual Threads (Project Loom) — JEP 444, the headline feature
Lightweight threads managed by the JVM, not the OS — you can spawn **millions**, not thousands.
```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (Order order : orders) {
        executor.submit(() -> processOrder(order)); // each gets its own virtual thread
    }
}
```
**Production scenario:** A Spring Boot service handling 50,000 concurrent slow downstream HTTP calls (each blocking for ~200ms). With platform threads, you're capped by thread-pool size (say, 200 threads) and requests queue up. With virtual threads, each request gets its own virtual thread; blocking I/O just "parks" the virtual thread cheaply without holding an OS thread.
**Answer:** This lets you write simple **blocking-style code** (no reactive/`CompletableFuture` chains needed) that scales like reactive code. Spring Boot 3.2+ has native virtual-thread support (`spring.threads.virtual.enabled=true`) — a common current interview topic: "why would you choose virtual threads over WebFlux?" → simpler code, same throughput for I/O-bound workloads, but WebFlux still wins for extreme low-latency/backpressure-sensitive pipelines.
**Gotcha to mention in interviews:** Virtual threads don't help CPU-bound work, and `synchronized` blocks used to "pin" the virtual thread to its carrier OS thread in early versions (largely fixed in later JDKs) — a known nuance.

### 2. Pattern Matching for `switch` (Finalized) + Record Patterns (JEP 440/441)
Destructure records directly in `switch`/`instanceof`.
```java
record Point(int x, int y) {}
record Line(Point start, Point end) {}

static String classify(Object shape) {
    return switch (shape) {
        case Line(Point(var x1, var y1), Point(var x2, var y2)) when x1 == x2 -> "Vertical line";
        case Line l -> "Line";
        case Point p -> "Point";
        default -> "Unknown";
    };
}
```
**Production scenario:** Parsing heterogeneous event payloads from a Kafka topic modeled as a sealed interface hierarchy (e.g., `OrderPlaced`, `OrderCancelled`, `PaymentFailed`) — record patterns let you destructure nested fields directly in the dispatch logic, replacing verbose chains of `instanceof` + manual casting + getter calls.

### 3. Sequenced Collections (JEP 431)
New interfaces `SequencedCollection`, `SequencedSet`, `SequencedMap` — unified way to access first/last elements and get a reversed view, across `List`, `LinkedHashSet`, `LinkedHashMap`, etc.
```java
List<String> list = new ArrayList<>(List.of("a", "b", "c"));
String first = list.getFirst();   // no more list.get(0)
String last = list.getLast();
List<String> reversed = list.reversed();
```
**Production scenario:** A recent-activity feed (`LinkedHashMap` keyed by timestamp) — previously getting the "last inserted" entry required an awkward iterator dance; now it's a direct `getLast()` call, reducing bug-prone index arithmetic in ordering-sensitive code (audit logs, undo stacks).

### 4. Structured Concurrency (Preview, JEP 453)
Treats a group of related concurrent subtasks as a single unit — if one fails, siblings are cancelled automatically; no more leaked threads on partial failure.
```java
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Supplier<Inventory> inv = scope.fork(() -> inventoryClient.check(sku));
    Supplier<Price> price = scope.fork(() -> pricingClient.get(sku));
    scope.join().throwIfFailed();
    return new CheckoutResult(inv.get(), price.get());
}
```
**Production scenario:** Same fan-out call as the `CompletableFuture` example above, but if the inventory call fails, the pricing call is **automatically cancelled** rather than continuing to run and wasting resources — solves a real production problem of "orphaned" async tasks from partial failures in fan-out/fan-in call patterns.

### 5. Scoped Values (Preview, JEP 446)
Immutable, efficient alternative to `ThreadLocal` for sharing context (e.g., request ID, tenant ID) across a call chain — designed to work well with virtual threads (avoids `ThreadLocal`'s per-thread memory cost multiplied across millions of virtual threads).
```java
static final ScopedValue<String> REQUEST_ID = ScopedValue.newInstance();
ScopedValue.where(REQUEST_ID, requestId).run(() -> handleRequest());
```
**Production scenario:** Propagating a correlation/trace ID through a request's call chain for logging (MDC-style) — with millions of virtual threads, `ThreadLocal` inheritance becomes memory-expensive; `ScopedValue` is immutable and cheaper.

### 6. Generational ZGC (JEP 439)
ZGC now separates young/old generations (like G1) — cuts GC CPU overhead and pause times further for large-heap, low-latency applications.
**Production scenario:** A high-frequency trading or ad-bidding system with a 64GB+ heap needing sub-millisecond pauses under sustained allocation pressure — Generational ZGC significantly reduces GC-related latency spikes compared to non-generational ZGC or G1.

### 7. String Templates (Preview, JEP 430 — later withdrawn/reworked, not finalized as originally proposed)
```java
String name = "Sanjay";
String msg = STR."Hello \{name}, your order total is \{total}";
```
**Note:** Was preview-only in 21 and 22, and was **removed** from Java 23 pending redesign — worth knowing this feature's status changed if it comes up, since it never became stable API.

### 8. Key Encapsulation Mechanism API (JEP 452)
Standard API for KEM algorithms used in hybrid public-key encryption — relevant for security/crypto-heavy services adopting post-quantum-ready cryptography standards.

### 9. Unnamed Patterns/Variables & Unnamed Classes (Preview)
`var _ = someCall();` to explicitly discard unused values; simplified `main` method syntax for quick scripts/teaching — mostly finalized in later versions (21/22 previews).

## Quick Interview-Ready Comparison Table

| Feature Area | Java 8 | Java 11 | Java 17 | Java 21 |
|---|---|---|---|---|
| Functional programming | Lambdas, Streams, Optional | — | — | — |
| Concurrency model | CompletableFuture | — | — | Virtual Threads, Structured Concurrency |
| Data modeling | POJOs + Lombok | — | Records, Sealed classes | Record patterns |
| Control flow | if/switch (statement) | — | Pattern matching switch (preview) | Pattern matching switch (final) |
| Collections | Stream API | — | — | Sequenced Collections |
| HTTP | Third-party libs | Native HttpClient | — | — |
| GC | Parallel GC default | Epsilon, ZGC (exp.) | ZGC production-ready | Generational ZGC |
| Security | — | — | Strong JDK encapsulation | KEM API |
| Migration pain point | — | JAXB/JAX-WS removal | Reflection access breaks (`InaccessibleObjectException`) | — |

## Most-Asked "Why Upgrade" Interview Answer
If asked "why should a company migrate from Java 8 to 17 or 21 in production":
1. **Java 8 is out of free public support** (Oracle) — security patch risk.
2. **Virtual threads (21)** can replace complex reactive stacks for I/O-bound services, simplifying codebases (fewer WebFlux/`CompletableFuture` chains) while improving throughput.
3. **Records + sealed + pattern matching (17/21)** reduce boilerplate and catch missing-case bugs at compile time instead of production incidents.
4. **Generational ZGC (21)** reduces GC pause-related latency SLA violations for large-heap services.
5. **Performance**: each LTS generally improves startup time, memory footprint (JIT/C2 improvements), and GC throughput out of the box — often a "free" win just from the upgrade.
